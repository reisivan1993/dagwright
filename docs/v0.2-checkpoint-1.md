# v0.2 checkpoint 1: local Spark/Iceberg execution

Status: complete and verified 2026-08-25.

This checkpoint turns the v0.1 generated customer-analytics Spark artifact into the first real data
execution test. It uses Apache Spark 3.5.5 and Apache Iceberg 1.11.0 with a filesystem-backed Hadoop
catalog under `build/reference-execution/warehouse`. It requires Java 17 but no PostgreSQL, REST
catalog, object store, orchestrator service, or control-plane service.

The runtime follows the Apache Iceberg Spark integration documented at
<https://iceberg.apache.org/docs/latest/spark-getting-started/>: the matching
`iceberg-spark-runtime-3.5_2.12` JAR is the only Iceberg runtime added to Spark.

## Run

```sh
make verify-reference
```

Checkpoint 2 exposes the same execution through a reusable suite and public command:

```sh
uv run --extra execution dagwright verify examples/customer-analytics/dataproduct.yaml \
  --suite examples/customer-analytics/verification.yaml \
  --output build/verification
```

The suite declares fixture views, deterministic row ordering, expected rows/schema,
negative-control fixture replacements, and the number of idempotency attempts.

The command regenerates the compiler golden bundle, runs its generated
`spark/build_customer_engagement.py` SQL, and verifies:

- exact output rows and schema after reading the Iceberg table;
- declared `not_null` and `unique` rules;
- negative controls containing one null identifier and one duplicate identifier;
- two replace-output attempts have the same three rows and output digest;
- evidence matches `tests/golden/execution/customer-analytics.evidence.json` byte-for-byte.

Inspect evidence independently:

```sh
uv run dagwright inspect-evidence build/reference-execution/evidence.json
```

The evidence intentionally excludes timestamps, host paths, Spark job IDs, and Iceberg snapshot IDs.
It contains contract/IR digests, fixture hashes, canonical output digests, schema, quality outcomes,
negative-control outcomes, and per-attempt row counts.

The real-engine pytest integration is opt-in because it downloads and starts Spark:

```sh
DAGWRIGHT_RUN_SPARK_TESTS=1 uv run pytest -m spark_integration
```

No LLM, agent, MCP, UI, PostgreSQL persistence, additional orchestrator, microservice, Kafka,
Kubernetes, Temporal, vector database, or Rust component is introduced.
